- 用户有**阿里云北京节点，2 vCPU / 2 GiB 内存**，机器操作系统、端口、当前进程、SSH 连通性、磁盘/流量、防火墙/域名尚待环境检查，**请你亲自读取并报告，不重复询问用户已知的地域和资源**。

### 五步执行顺序
1. **盘点已有**：用当前 Codex 实际可访问的技能列表（例如 /skills）、仓库及用户目录中的 .agents/skills、AGENTS.md、已安装插件/MCP、既有依赖、Open WebUI 扩展能力和历史代码。无法检查的本地条件明确标「未核验」，不可猜。
2. **优先官方**：OpenAI 现行 Codex Plugins/Skills 文档、Open WebUI 的内置 Tools、Functions、MCP/OpenAPI、目标编程语言/框架官方组件与教程。先使用已有而且兼容的功能，避免重新造聊天、登录和权限管理。
3. **缺项查社区和 GitHub**：需要哪项能力就有针对性地查对应的 Skills、插件、模板、设计系统、UI/UX 实践、轻量动画库、图表、测试、安全与工程质量工具。核对原项目维护、实际源码、许可证、依赖、资源占用、最新兼容性、风险和成本。
4. **按需最小验证**：当阶段只挑真正有价值的少量候选，运行最小测试，再决定采用。不允许不审查来源就运行第三方脚本或安装高权限 Skill；调用私密资料、访问密钥、需要付费、修改系统设置、扩展网络权限前先取得用户明确同意。
5. **没有合适现成资源时**：使用已验证框架的标准能力编写必需业务代码，说明查过哪些候选及为何不采用；不得“自创一个现成 Skill”冒充找到资源。反复使用且确实有价值的专属工作流才考虑设计自定义 Skill，**不必为了此阶段强行创建**。

## 2. 分阶段完成，避免反复造轮子

### 阶段 0｜只读环境审计（先执行、给出事实报告）
1. 检查 GitHub 当前分支、工程文件、已有服务，检查服务器是否可从 Codex 工作环境实际访问。
2. 如果有获授权的服务器 SSH/云环境，再**只读**查询 OS、架构、内存、磁盘、Swap、运行容器、端口、网络出口和备份状况。不要停止现有服务、更改防火墙、重置系统。
3. 对照 Open WebUI 最新官方文档，选择与系统兼容、固定版本的 **slim**。先查依赖与资源。北京公网访问必须合规；优先评估无需把管理界面暴露到公网的两人接入方案。不得用公网裸 IP/换端口规避 ICP。
4. 输出`环境检查结果/风险/已存在资源/可以继续的下一操作`。**如果缺 SSH 授权、DeepSeek API Key 或可访问的服务器，继续完成本地代码与测试，而不是假装已经部署。**

### 阶段 1｜真实可用的聊天底座
1. 保留旧版本源码；在新目录开发，不修改历史 `prototype/v0.1~v0.6`。
2. 配置 Open WebUI slim（保留数据卷、固定 WEBUI_SECRET_KEY、无预制本地大模型、不过量开后台服务）；默认关闭不必要资源密集型功能。
3. 连接**真实** DeepSeek API，明确标记任何模拟回退。连接前配置最小可用权限、单日/每次调用预算上限。
4. 两个真实账户，个人聊天彼此不可见；创建仅两名用户可读写的 Channel，AI 被 `@模型` 提及时回答，回答能够被双方看到。不要把公开 Channel 错配为全站可见。
5. 用两个独立浏览器登录测试，记录真实对话与 `@模型` 结果、用户数据隔离和 RAM 峰值。

### 阶段 2｜配对 + 双方公开档案/科学画像
1. 账号映射到 `couple_id`，只有已配对账号有权互相读档案；**只档案主人可以编辑、确认、删除本人资料**。
2. 按 D-45 实施对话建档，详情见 `docs/PROFILE_QUESTIONNAIRE_FINAL_V1.md`。DP 在私聊中根据真实自述提出可纠正的档案内容。
3. 用图文卡展示本人确认的偏好与细节，区分公开内容及私下候选；自由叙述不生成标准量表分数。
4. 双方个人聊天历史默认各自可见；聊天中新增偏好先产生待确认提议，只有本人明确选“加入公开档案”才写入，才允许另一个用户或共同 AI 读取。
5. 不要额外建立旧方案「两个私人功能空间/三层隐私开关」；旧 `PRIVACY_AND_SPACES_DRAFT.md` 已过时。

### 阶段 3｜真实 AI 功能导演的最小闭环（最重要）
1. 使用一个真实 DeepSeek 模型服务承担意图理解、内容生成和模块选用；不是固定关键词路由、不是四个昂贵 Agent。
2. **方案 B 已认可**：AI 可自动生成草稿；个人聊天的 AI 草稿只在本人可见，共同 Channel 的草稿两人可见；**正式写入/修改共同模块时才触发确认**，不能因生成而冒充已保存。
3. 实现有真实读/写/查看详情/编辑/确认的最小三个模块：**约会/共同计划、共同心愿、回忆或日程**。可在最初闭环以其中两个串联，第三个实现浏览和修改。**小宇宙必须作为独立模块保留有可进入的占位/既有演示功能**，后续再接真实 AI 故事与场景，不删掉。
4. AI 根据已公开档案生成模块草稿 → 用户打开详情并手动修改 → 一张合并确认卡 → 服务端校验后写入共享数据 → 配对另一方读取一致 → 用户反馈影响下一次建议。不得只在聊天里描述“我已创建计划”，必须能查询到后端持久化对象。
5. 给模型暴露白名单工具（读取已确认档案、读取模块详情、准备草稿、提交待确认更新等），**所有真正写操作后端验证 `actor_id` 与权限和确认凭据**，不能信任模型自己说已获授权。
6. 触发方式首版以用户消息/明确修改为主，轻量规则检查已有日程；**不运行全天候无限消耗 Token 的代理进程**。未来功能列表保留扩展接口但不假装所有模块已实现。
7. 任何单独聊天里策划的秘密惊喜，不得通过共同卡片、群聊、通知或模型回答泄漏。公开个人档案不意味着公开个人聊天内容。
8. 前端**渐进披露**：首页一屏只保留 AI 主入口和少量已生成的关键卡片；模块作为展示入口，点开详情再展开编辑；拒绝过量按钮与密集文字。

## 3. 实际验收（必须有可核验记录）
- 真实两账户双手机/隔离浏览器测试：共同 Channel、个人对话隔离、公开档案互读但只能本人修改。
- A 说“我不喜欢人多”，未确认公开前 B 看不到；本人确认后共享档案更新，B 看到，AI 约会推荐改变。
- 共同群聊 `@AI 周末去哪` 结合双方档案生成**真实后端存储的约会草稿**；修改、确认并关联共同心愿/日程后，B 能查询同一个版本。
- A 单独准备惊喜不能在 B 的列表和 AI 结果中泄漏；也不能通过模棱两可的“有惊喜”暗示。
- 遇到 API 失败、预算限制、网络不通时明确告知“功能不可用”，**不得用模板伪装成真 AI**。
- 做基础的读取越权、未授权写入、重复提交、防泄漏回归测试，记录版本、命令、日志路径、错误、内存/实际用量，给可复现步骤。
- 用真实服务器部署测试才能宣布“已能在两台手机使用”；代码提交成功、HTML 运行或一次 Playwright 点击**均不能当成真实部署与双人验收**。
