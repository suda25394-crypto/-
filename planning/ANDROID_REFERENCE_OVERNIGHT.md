# 双生宇宙 Android 夜间交接 · 2026-11-19（北京时间）

**今晚交付一个能安装的新测试版。** 苏打实际使用 0.4.1+5 后反馈明显卡顿和 bug，想让 Codex 学习他指定的同类 App，醒来能亲自比较效果。此前只做诊断的阶段已结束。本轮允许在现有 Android 客户端做可逆改动、测试、构建及发布独立测试包。dot 负责协调和验收，Android Codex 负责实现和打包。谁已有在跑的开发任务就继续那一个，避免两个任务同时改同一分支。

## 收到任务就开工

1. 读取用户在本对话或开发对话交付的参考 APK、本机路径、源码或官方商店链接。记录可核对的应用名称、包名及版本。只有商店链接时，可从公开介绍、截图和能正常使用的页面学习；只有安装包时，区分可见实现、运行观察和推测。用户没有指定样本时，不猜竞品。先完成以下自家修复，回执注明参考材料缺失；夜里收到材料再补做对照。
2. 在现有 Android 工作区执行 `git fetch origin`，核对 PR #1、当前开发分支和未提交工作。用户正在用的发布版为 `0.4.1+5`，打包提交 `ff47348`。从最新兼容代码继续。保留「我们仨」默认群聊、独立 DP 私聊、四栏导航、真实账号及权限、云端记忆和现有 R2 后端。把上个包漏掉的新版紫色实装到 Android，颜色以 main 的 `prototype/white-purple-review/index.html`（修订 `d21dde0`）为准。
3. 对参考 App 选一至两条最值得借鉴、用户明早能亲手比较的交互，优先看打开聊天、滑动、发消息、切私聊或首次进入。举例：「点发送马上出现自己的气泡」「切回聊天时停在刚才的位置」。写下对方实际表现、我们的差距，在自己的代码里独立实现适合的做法。APK 和对方的代码、美术、标识不纳入我们的仓库。保留我们自己的产品定位和配色。

## 先测最卡的路径，直接修并复测

- 在同设备、同数据量、同构建模式下比较我们旧版和候选版。分别计时「打开到能输入」「点发送到自己看见气泡」「对方收到消息」「DP 开始或完成回复」。查聊天列表滑动、软键盘、群聊和私聊来回切换，检查是否重复请求、全页重绘或丢失滚动位置。调试包与发布模式的数字分开；测不了的项明确写待测。
- 按证据修最影响日用的卡顿及能复现的 bug。用合成双账号及模拟模型响应验收，不消耗正式 DP 额度。验证发送失败可重试、弱网不重复发、A 的私聊不进 B 账号、普通群消息不调模型、强停重开恢复。服务端已上线；若发现根因在服务端，先记录证据和兼容修复方案，可交付不依赖生产变更的客户端改进。
- 用户正在休息。常规取舍可自行决定，遇到一个阻塞继续其他可做项。涉及重置账号、清理真实数据、变更服务器或新增费用时，用现有备选方案继续，单独留下待本人决定的一句话。不代替用户批准系统授权。参考 App 暂缺时，也交出能测出的改进，不称作已完成竞品学习。

## 明早交付给苏打

- 沿用原应用 ID、签名，versionCode 高于当前已发布版本；独立测试 Release 保留旧包装回退参考。从发布处重新下载 APK，核对哈希、实际版本及签名，验证从旧版覆盖安装，保留数据。若发布渠道确实不可用，交付经过核对且用户可访问的本机 APK 路径，并准确说明下载状态。
- 在开发分支留简短验收回执并在原 PR 加入口。第一行给新 APK 下载入口；随后只写「借鉴了什么」「哪项实测变快或修好」「打开后用哪两个动作感受区别」「还有哪些只在模拟器测过」。对照结果给设备、构建模式和前后数值；无法公平比较时直说。交接文档、旧 APK、改版截图都不能单独算作这次的软件交付。

## dot 夜间如何处理问题

先看原 Android Codex 会话，再看 PR #1、开发分支、Releases 和本任务的回执。原会话可连接时，将用户已给的参考附件或本机路径和本任务交到原会话，确认 Codex 已收到；已在运行就继续跟踪。仅在卡住且已有明确下一步时跟进一次。不能访问原会话时，用可核实的仓库证据说明进度，标明任务是否实际投递，把上述同一条启动指令交给苏打。一个失败步骤不得冒充整体失败，一个已推送的提交也不能冒充 APK。涉及必须由本人进行的审批、解锁或真机验证，留到早上集中说明。
