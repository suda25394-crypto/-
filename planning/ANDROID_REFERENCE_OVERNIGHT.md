# 双生宇宙 Android 夜间任务书 V2｜把参考 App 的好功能做到新版里

2026-11-19，北京时间。本版按苏打最新要求执行，替代同路径的第一版交接。今晚要交付可覆盖安装的新 Android 测试包，让两个人醒来可以亲自使用从指定参考 App 学来的新功能，同时体验流畅度和稳定性改进。功能选择和常规实现由 Android Codex 负责，dot 跟进交付。

## 一、找出值得引入的功能

1. 读取原开发对话中的参考 APK、源码、本机路径或用户指定的官方链接，核对应用名与版本。走一遍能正常访问的主要入口、二级页面和双方互动流程。安装包看不到的服务端设计标为未知。保留有助复核的页面名称、步骤或可公开链接，竞品安装包、专有素材和代码留在仓库外。
2. 用双生宇宙已发布的 `0.4.1+5`（源码 `ff47348`）和 PR #1 最新 Android 代码作对照。按用户要完成的事情比较。把「已有且可用」「入口存在、流程未做完」「完全缺少」分清。功能同名时，比较双方实际能做什么。有真实用处的细节、跨模块的流程、与现有十二个入口不同的玩法也纳入。
3. 简要记下「参考 App 里怎么用 → 我们缺哪一步 → 在双生宇宙里做成什么」。从用户价值、两人使用频率、实现与运行成本判断优先级。主动做成多项有用且当晚能验证的功能，数量由样本和完成度决定。只有改颜色、修卡顿、添入口或做竞品清单，新增功能一项仍算待交付。若某项工作量大，完成一段能独立使用的流程，标清余下部分，继续做其他可交付项。
4. 尚未拿到指定样本时，先核对本方功能、修 bug、做性能基线；拿到样本就回到功能开发。若整个窗口都取不到，交付独立完成的改进并把参考功能列为阻塞；不得猜测用户指的是哪款 App。

## 二、实现，让两个人能用

- `git fetch origin` 后核对当前 Android 分支和工作区的新改动，接着原任务做。群聊「我们仨」、独立的 DP 私聊、底部四栏、真实账号及云端记忆继续作为基础。选择最合适的现有页面安放入口；即使适合放进现有模块，新增能力也应当有明确的用户操作、结果和再次打开后的状态。
- 设计时问清三件事：谁创建、对方什么时候能看到、DP 在哪一步能帮上忙。共享功能用两个独立测试账号完成 A 操作、B 接收或参与、两边重开再查看的流程；个人功能验证本人可见。能利用现有数据模型和接口的直接复用。DP 可根据用户意图打开模块、建议或起草操作；普通点击、保存和同步用已有业务逻辑，避免额外付费调用。
- 需要新增服务接口时，可以实现向后兼容的服务端改动、数据迁移和测试，附 Muse 可用的部署材料。分别写明本地验证和生产可用状态。当前 R2 可用的成果先交付；依赖未部署服务的功能要显示实际可用状态。
- 视觉采用白色、正紫、同色系淡紫和中性文字。上版交互稿可参照布局与紫色块的位置，色相以本次决定为准。白底、白卡片；主要按钮和本人气泡用清晰的葡萄紫，聊天底和选中项用它的淡色。可从主紫 `#8038A0`、淡紫 `#F1E7F6`、白 `#FFFFFF` 起步，自行核对真机文字对比。收掉偏蓝的靛紫、蓝色高亮和蓝紫渐变；用户自己上传的照片保留原色。
- 同步处理卡顿和可复现的 bug。在相同设备、构建模式和数据条件下比较旧包与候选包，重点测打开到可输入、滑历史、发送到自己的气泡出现、另一端收到、切换私聊。把网络和等待 DP 回复的时间单列。验证弱网重试、群私聊隔离及强停恢复。测试使用合成账号与上游，记录能复核的前后数值。

## 三、无人值守与明早交付

用户正在休息。普通功能取舍、实现和可逆修复自主完成。单项受阻就做其他项。需要新增付费、实际生产变更、重置账号或清理真实数据时，记录具体原因和最小待办，留到早上。已有开发线程继续执行，避免两个任务同时写同一分支。

沿用同一应用 ID 和签名，提高版本号，保留旧发布件；从发布位置重新下载新 APK 并核对哈希、签名和覆盖安装。若发布通道不可用，先给用户实际可取得的安装文件，并注明发布状态。提交代码及简短回执，在原 PR #1 留入口。第一行给 APK，随后用表格列出「实际新增或补全的功能／从哪个页面点进去／另一台手机应该看到什么／已在哪种环境验证」。另用几句话交代卡顿和 bug 的修复结果、待部署或待真机确认项。把用户起床就能试的新玩法放在最前面。

dot 核对的是新版 APK 里实际有些什么。检查原 Android Codex 线程、PR、发布件和验收记录；若 Codex 还按旧版只修性能，且原线程可达，把这份 V2 交给同一个 Codex 接着做。若只有修复包，就如实发出可用包并标明新增功能待完成。没有样本、无法投递或还没有新版，都把具体状态说清楚。
