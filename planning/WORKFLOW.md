# 协作规则｜AI 情侣生态项目

更新：2026-11-16。

## 唯一长期信息中心
GitHub `suda25394-crypto/-`。关于产品目标，以**用户最新明确决定**和仓库已确认决策为准；代码与进度用仓库提交/可验证记录核对，不能只根据聊天摘要想当然。

## AI 接手阅读顺序
1. `README.md` 了解**AI 主导情侣生态**总定位；
2. `docs/DECISIONS.md` 了解确认要求与纠偏；
3. `docs/AI_CORE.md` 了解关系记忆、功能导演、秘密策划师、关系守护者；
4. `planning/PROGRESS.md` 检查哪些真正实现了；
5. 只读本次任务涉及的模块文档/代码，减少不必要的上下文和费用。

## 方向判断优先级（先读再动手）

**顶层产品意图（AI 主导情侣超级 App） > 长期“越用越懂”与动态编排机制 > 可联动的功能生态 > 独立模块 > 讨论中的具体示例与选择题 > 模型/视觉实现方式。**

用户说某个功能“惊艳”“挺不错”，不能理解为该功能取代整体定位。用户首次画像问卷仅是一种可选设想，不等于强制完整人格测试；四种 AI 能力是统一中枢的职责而非四个独立 Agent；小宇宙只是被调用的一个模块。遇到历史冲突，优先对照 [逐轮方向审计](../history/DIRECTION_AUDIT_2026-11-16.md)。

## **红线：不得再发生小宇宙中心化漂移**
- 小宇宙/角色/故事是可被 AI 调用、也能独立进入的核心模块之一。
- **不是**整个产品的唯一概念、首页要求、数据库主轴或所有用户行为的目的地。
- 功能导演必须能在不调用小宇宙的情况下联动约会、预算、日程、礼物等功能。
- 如果开发内容把全应用做成模拟宇宙游戏，需要先回看 `docs/PROJECT.md`，不能自行改变已确认定位。

## GPT、Codex、DSH
- GPT 与用户共同形成需求、维护信息与合理判断；
- Codex、DSH 可按具体授权承担开发、测试、修复；
- 尚未锁定固定分工，也不默许改用付费技术栈。
- 不以“虚拟世界很酷”为理由抢占其他生态模块的优先级。

## 决策/创意/实施的分界
- 探索点子 → `ideas/BACKLOG.md`。
- 用户明确采用 → `docs/DECISIONS.md`，并标注日期。
- 实现与验收 → 代码/截图/测试 + `planning/PROGRESS.md`。
- 重要的纠错应保留到 `history/DISCUSSION.md`，而不是偷偷掩盖。

## 已有技能与成熟资源复用优先（2026-11-16）

Codex/DSH 在每个开发阶段先盘点已有 Skills、插件、MCP、Open WebUI 原生功能、仓库依赖；不足时查**官方现行目录 → 实际维护中的 GitHub/社区项目 → 组件/程序库/设计系统**。不仅查“技能包”，还要覆盖**手机 UI 审美、交互动效、图表、无障碍、代码质量、安全、自动测试、部署、开发工具和后端模块**。必须核对实际存在、许可证、版本、兼容性、资源与密钥权限；不允许自创不存在的 Skill 名称和安装路径或未经审查直接运行第三方脚本。

**只按阶段查真正需要的资源**；检查后继续开发，不为收集技能而长期停工。记录采用/拒绝理由与最小验证到 planning/RESOURCE_REUSE_AUDIT.md（由实际施工的 Codex 建立），切勿将「候选」当「已安装」。详见 [Codex 开工指令](CODEX_DEMO_KICKOFF.md)。

## 安全与成本
- 在真正联网之前，不要提交密钥和真实情侣隐私；
- 每个用户有其信息授权与撤回权，不能为了策划惊喜跨越一方保密边界；
- 先小范围规则/模型验证，再扩充能力；能不买新订阅就不买；
- 不让模型任意执行代码、扣款或发送未获确认的信息。

说明更改文件、commit、可复现验收步骤、已知限制、是否经过用户验收。失败就写失败，不虚构。
