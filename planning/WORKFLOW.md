更新：2026-11-16（多 AI 分工定稿 v2）。

## 唯一长期信息中心
GitHub `suda25394-crypto/-`。关于产品目标，以**用户最新明确决定**和仓库已确认决策为准；代码与进度用仓库提交/可验证记录核对，不能只根据聊天摘要想当然。

## AI 接手阅读顺序
1. `README.md` 了解**AI 主导情侣生态**总定位；
2. `docs/DECISIONS.md` 了解确认要求与纠偏；
3. `docs/PROJECT.md` 了解总体定位与差异化；
4. `docs/AI_CORE.md` 了解关系记忆、功能导演、秘密策划师、关系守护者；
5. `planning/PROGRESS.md` 检查哪些真正实现了；
6. 只读本次任务涉及的模块文档/代码，减少不必要的上下文和费用。

## 方向判断优先级（先读再动手）

**顶层产品意图（AI 主导情侣超级 App） > 长期“越用越懂”与动态编排机制 > 可联动的功能生态 > 独立模块 > 讨论中的具体示例与选择题 > 模型/视觉实现方式。**

用户说某个功能“惊艳”“挺不错”，不能理解为该功能取代整体定位。用户首次画像问卷仅是一种可选设想，不等于强制完整人格测试；四种 AI 能力是统一中枢的职责而非四个独立 Agent；小宇宙只是被调用的一个模块。遇到历史冲突，优先对照 [逐轮方向审计](../history/DIRECTION_AUDIT_2026-11-16.md)。

## **红线：不得再发生小宇宙中心化漂移**
- 小宇宙/角色/故事是可被 AI 调用、也能独立进入的核心模块之一。
- **不是**整个产品的唯一概念、首页要求、数据库主轴或所有用户行为的目的地。
- 功能导演必须能在不调用小宇宙的情况下联动约会、预算、日程、礼物等功能。
- 如果开发内容把全应用做成模拟宇宙游戏，需要先回看 `docs/PROJECT.md`，不能自行改变已确认定位。

## 多 AI 分工（定稿 v2，2026-11-16，用户与 GPT 确认）

| 成员 | 核心职责 | 不应该做什么 |
|---|---|---|
| 用户 | 产品最终决策、方向选择、账号授权、付费审批、成果验收 | 不必亲自处理技术细节 |
| GPT | 产品总纲、需求设计、架构决策、文档维护、技术方案审查 | 不擅自替用户决定产品方向 |
| Codex | 主力开发、代码编写、测试、修复、开发文档 | 不擅自改变已确认的产品设计 |
| Muse | 服务器运维、部署、日志检查、运行状态监控、独立验收、技术调研 | 不擅自修改产品方向和代码架构 |

**Codex 负责把软件造出来，Muse 负责让软件稳定运行。** 两者可以协作，但代码负责人与部署负责人必须分清。

DSH 不在团队里（2026-11-16 用户决定去掉）；原本地开发辅助与专项测试缺口默认归 Codex，需要时再议。

分工以本表为准；不默许改用付费技术栈。不以“虚拟世界很酷”为理由抢占其他生态模块的优先级。

## 交接制度与三种状态

**交接链**：GPT 制定需求 → Codex 实现并提交代码 → Muse 部署、检查日志、独立验收 → GPT 对照原始需求复核 → 用户最终体验和验收。

**GitHub 是项目共同记忆**：动手前先读 `README.md`、`docs/DECISIONS.md`、`docs/PROJECT.md`、`planning/PROGRESS.md`；完成工作后留下实际成果和测试证据。

**三种状态**：
- 已决定：不能擅自更改。
- 正在探索：可以提出不同意见。
- 已实现：必须有代码和测试证据。

任何 Agent 说一句「完成了」，其他 Agent 不能直接相信，要看证据。

暂不开发复杂的 Agent 通信系统，以 GitHub 交接为准；任务、交接记录、测试结果统一放仓库，减少用户来回搬运信息的工作量。

## 决策/创意/实施的分界
- 探索点子 → `ideas/BACKLOG.md`。
- 用户明确采用 → `docs/DECISIONS.md`，并标注日期。
- 实现与验收 → 代码/截图/测试 + `planning/PROGRESS.md`。
- 重要的纠错应保留到 `history/DISCUSSION.md`，而不是偷偷掩盖。

## 已有技能与成熟资源复用优先（2026-11-16）

Codex 在每个开发阶段先盘点已有 Skills、插件、MCP、Open WebUI 原生功能、仓库依赖；不足时查**官方现行目录 → 实际维护中的 GitHub/社区项目 → 组件/程序库/设计系统**。不仅查“技能包”，还要覆盖**手机 UI 审美、交互动效、图表、无障碍、代码质量、安全、自动测试、部署、开发工具和后端模块**。必须核对实际存在、许可证、版本、兼容性、资源与密钥权限；不允许自创不存在的 Skill 名称和安装路径或未经审查直接运行第三方脚本。

**只按阶段查真正需要的资源**；检查后继续开发，不为收集技能而长期停工。记录采用/拒绝理由与最小验证到 planning/RESOURCE_REUSE_AUDIT.md（由实际施工的 Codex 建立），切勿将「候选」当「已安装」。详见 [Codex 开工指令](CODEX_DEMO_KICKOFF.md)。

## 安全与成本
- 在真正联网之前，不要提交密钥和真实情侣隐私；
- 每个用户有其信息授权与撤回权，不能为了策划惊喜跨越一方保密边界；
- 先小范围规则/模型验证，再扩充能力；能不买新订阅就不买；
- 不让模型任意执行代码、扣款或发送未获确认的信息。

## 交付格式
说明更改文件、commit、可复现验收步骤、已知限制、是否经过用户验收。失败就写失败，不虚构。


## 重要变化的主动同步规则（2026-11-17，用户明确授权）

GPT 作为项目总控，**应自行判断项目变化是否重要，并主动同步 GitHub；无需每次向用户询问“要不要记录”**。

### 应主动同步的变化
- 用户确认或撤销的产品决策、核心定位和边界；
- AI 核心架构、功能导演权限、模块关系与隐私规则；
- 技术底座、部署架构、模型/API、关键依赖或成本策略变化；
- 服务器账号权限、网络入口、安全状态、部署/运行状态；
- Codex / Muse / GPT 职责变化与跨 Agent 交接规则；
- 重要开发里程碑、测试/验收结果、失败原因和下一步阻塞项。

### 按状态写入正确文件
- 用户明确确认的方向 → docs/DECISIONS.md；
- 当前项目事实与架构 → 对应 docs/*.md；
- 已实现、已部署、已测试、待验收 → planning/PROGRESS.md，并附证据；
- 服务器交接 → planning/SERVER_HANDOVER_*.md，必须脱敏；
- 尚未决定的创意 → ideas/BACKLOG.md，不能冒充正式决定；
- 重要纠错与历史原因 → history/，保留原始脉络。

### 安全和准确性红线
- 不把聊天中的口头“完成”直接写成已验收；检查提交、文件、日志或测试证据。
- 不把方案、候选技术、Codex 计划冒充已安装/已部署/已通过测试。
- 密码、私钥、API Key、Token、Cookie、会话凭据、个人隐私**永远不得写入 GitHub**。只记录凭据曾暴露、需轮换等风险事实，不保存秘密本身。
- 若源材料含秘密，先制作脱敏摘要；不把原始附件照搬到仓库。
- 更新后检查 README、DECISIONS、PROGRESS、WORKFLOW 等入口是否互相矛盾；必要时同步修正过时摘要。
- 完成后简要告诉用户改了哪些文件、commit 和仍待处理的事项。

此规则是 GPT 的持续工作职责，不代表每次聊天都必须提交一次 commit；只在变化具有项目长期价值时写入。
