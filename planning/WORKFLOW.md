# 仓库协作方式｜GPT × Codex × DSH

## 唯一事实源
**GitHub `suda25394-crypto/-` 是情侣 App 项目的长期资料仓库。** 聊天摘要只是辅助线索；发生冲突时先核对仓库内有证据的记录，再向用户确认重大改动。

## 文件职责
- `README.md`：总导航，必须能让新人 1 分钟找到资料。
- `docs/DECISIONS.md`：确认的产品边界，不得擅自改。
- `docs/PROJECT.md` + `docs/FEATURES.md` + `docs/EXPERIENCE.md`：产品方向、功能和体验。
- `docs/TECH.md` + `docs/BUSINESS.md`：技术与成本假设。
- `research/`：竞品、公开证据和来源可信度。
- `ideas/`：尚未采用的创意储备。
- `planning/PROGRESS.md`：当前进度、证据、待办。
- `history/`：讨论与关键转向摘要。
- `prototype/v0.1/`：历史原型快照。后续不要静默覆盖旧版本。

## 读写与分工
- **GPT**：与用户共同定义方向、检索评估、维护文档/决策一致性；并不自动拥有所有开发决策权。
- **Codex、DSH**：在用户授权的范围内开发、测试、修复，提交可复现的代码与结果。
- 未正式指定“哪个 Agent 固定负责哪一块”，不能自行假定领导链。

每次接手先读 `README.md` → `docs/DECISIONS.md` → `planning/PROGRESS.md` → 对应模块，避免全仓搜索与无效成本。

## 决策和执行边界
- **脑洞** → 写到 `ideas/BACKLOG.md`；
- **用户明确确认** → 写到 `docs/DECISIONS.md`；
- **实际产出** → 放代码或文档并保留版本/commit；
- **进度变化** → 更新 `planning/PROGRESS.md`，列明可追溯证据；
- **未验证的市场说法** → 写 `research/`，注明不确定性。

禁止把“AI 建议”“后续可做”“代码占位”和“用户已完成验收”混为一谈。

## 省钱/防返工
- 先检查现有原型，再考虑重构；不要仅为了最新框架迁移。
- 可本地模拟的功能，先本地验证；
- 新增付费 API/云服务先测成本、限额、失败行为；
- API Key/密钥不得提交仓库，不得出现在前端；
- 涉及两人聊天、隐私、个人资料的真实数据不应提交此仓库。

## 每次开发交付
一笔有说明的 commit + 修改文件 + 本地验证步骤 + 仍未解决的问题。若未运行测试，要明确写“未测试”，不要编造测试通过。
