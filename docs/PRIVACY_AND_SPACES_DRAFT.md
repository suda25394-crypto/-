# 双人空间、AI 保密与共享权限模型｜讨论草案 V0.1

**项目**：情侣 AI 超级 App；**日期**：2026-11-16。

> ⚠️ 本文将「用户已明确提出的架构要求」与「助手建议、尚待讨论/验证的权限细则」分开。不能将细则直接写成用户确认的决策；没有任何隐私隔离代码已实现。

## A. 用户明确提出（确认的产品意图）

1. 先完成双人配对，再让两个人接入同一个 AI 智能中枢。
2. 每人拥有**独立与 AI 私聊的空间**，另一方不能看到该空间的消息。
3. 另设一个**共同空间**，形态类似「我 + 她 + AI」三人群聊，双方在这里能看到彼此发给群聊的消息。
4. 用户现在要求讨论 AI 在私人空间、共同空间里**哪些可以说、哪些不能说**，隐私边界尚待形成最终规则。

**重要技术解释**：所谓同一个 DeepSeek，指一个统一的 AI 服务/人格与工具生态，不是合并两个私人聊天的消息历史，也不意味着模型可以无条件访问所有记忆。

## B. 助手建议：信息分类与默认边界（尚未确认）

| 信息来源/类别 | 默认可读者 | 默认可供 AI 使用的场所 | 能否透露给另一个人？ |
|---|---|---|---|
| 甲的私人聊天、私人记忆、私密模块数据 | 甲和为甲提供服务的 AI 请求 | 甲的私人会话 | 否，除非甲明确分享 |
| 乙的私人聊天、私人记忆、私密模块数据 | 乙和为乙提供服务的 AI 请求 | 乙的私人会话 | 否，除非乙明确分享 |
| 双方共同空间发布的消息 | 双方 + 群内 AI | 共同空间以及各自读共享资料的请求 | 已在群里可见，可用于群内答复；**不自动写入长期记忆** |
| 双方明确发布/授权为共同资料的模块内容 | 双方 + 授权工具及 AI | 各自、共同空间的已授权任务 | 可按共享设定展示与修改 |
| 某人私聊的秘密惊喜/礼物/情感倾诉 | 信息所有者 + 私聊 AI | 信息所有者私人空间 | 默认不能透露，包括暗示、通知、结果卡和“回答反向提问” |
| 第三方的敏感信息/一方对另一方的推测 | 按原始来源权限 | 不能自动转换成被谈论者的自述事实 | 不得伪装成对方已确认信息 |

**两个权限按钮不要混为一谈**：
- 「保存为我的私人记忆」= 允许下次在**我的私聊**使用。
- 「分享给另一方/共同空间」= 把指定内容交给共同空间；**不是**默认上传整段私聊。
- 「保存为共同长期记忆」= 是否给未来共同决策持续复用，建议独立确认。看到一条群消息 ≠ 同意永远保存。

## C. 助手建议：AI 的四条硬规则（尚未确认）

1. **谁能说**：用户在谁的空间发的消息，AI 就在同一个空间回复；除非用户明确主动发布/转发，否则不得把私聊转贴到群聊、另一方私聊、通知或模块结果。
2. **可以用什么**：私聊请求只给模型传当前用户私人资料与有权阅读的共同资料；群聊请求只给模型传群聊与共同授权资料。**默认不把另一方私聊摘要传给群聊模型**。
3. **可以透露什么**：AI 不能确认、否认、复述、总结、暗示另一人的秘密，也不能用另一人的隐私数据推断其感受；面对“她私下跟你说什么了？”应简短回绝，提出邀请对方主动分享。
4. **改动和发送**：AI 只输出提议/草稿；写入共享数据、发送消息、发布群通知、将私人数据分享到共同空间，都需要服务端校验和必要用户确认。提示词不能代替后台权限控制。

## D. 助手建议：跨空间协同的保守默认（尚未确认）

存在高级能力：「允许 AI 在不展示原文的情况下，用自己的私人偏好参与共同推荐」。此能力容易**间接泄密**，例如小众口味、对某人的评价和秘密安排可能被建议结果反向推断出来。

**建议两人 Demo V1 不开放隐式跨私聊信息推断**：
- 群聊只能使用共享资料和群聊信息。
- 私聊可调用明确共享的共同模块，但个人秘密只用于当事人私人建议。
- 若今后引入「私人偏好参与共同决策」设置，必须由信息所有者逐项、可撤销地授权**安全的偏好摘要**，不能直接给共享模型原始隐私，不保证仅靠“去名字”完全防泄漏。

## E. 助手建议：空间内模块如何显示

模块内容分两种所有权：`private(user_id)` 与 `shared(couple_id)`。
- AI 在我的私聊生成的约会草稿、惊喜、日记、个人心愿，默认是**私人草稿**，不会出现在对方模块列表；
- AI 在共同空间生成的约会计划、共同心愿、小宇宙公共场景，属于**共享内容**，双方能点开查看；
- 私人 → 共享，显式选择要发布的具体内容，可先预览隐私泄露风险；公开后可能已被对方看到，不能声称撤回等于消除对方记忆；
- 共享 → 私人，复制个人版本，不自动撤走既有共享版本。
- 共享模块修改：AI 展示变化摘要，编辑者确认后保存并同步；多端冲突应有修订版本或冲突提示。
- 关系记忆必须与功能内容的可见性分开：一个共享计划不等于共享计划里涉及的个人推断可自动归档为共同记忆。

## F. 助手建议：系统真正需要做的访问控制（不是 prompt）

服务端在每次 API 请求时确定 `actor_user_id`、`couple_id`、`space_id`、`authorized_scopes`，只检索有权访问的消息、记忆、模块文档；工具接口按资源所有者/权限二次验证。

概念数据：`users`, `couples`, `memberships`, `spaces`, `messages(space_id,author_id)`, `memories(owner_id,visibility,consent,source_id)`, `module_items(owner_scope,visibility,version)`, `tool_actions`, `audit_events`。实际实现字段由 Codex 设计后评审。

**同一个 DeepSeek API 并不自带可信的跨会话隐私墙**。请求上下文由应用后端按空间裁切；不能把全部私聊历史都传进模型，再要求“你别说出去”。API 提供方可能处理发送内容，隐私承诺须以相应合同/政策核对，不能保证私聊不经第三方服务器。

## G. 助手建议：防泄漏测试案例

| 场景 | 应有行为 |
|---|---|
| 甲私聊：“想给她买礼物，别告诉她” | 仅甲和其私聊 AI 可见；乙私聊、群聊、共享礼物卡无痕迹 |
| 乙问 AI：“他给我准备礼物了吗？” | 若来源只在甲私聊，不能回答具体有无，不能给暗示 |
| 乙私聊：“最近我不太开心” | 甲私聊或群聊 AI 不得将乙情绪当共享事实 |
| 甲在群里发布：“我喜欢安静餐厅” | 乙可以看到该群消息，但保存为共同长期记忆仍按独立授权流程 |
| 甲私聊：“她讨厌人多” | 只作为甲的说法，不能冒充乙本人已确认的偏好 |
| 乙私聊生成惊喜计划 | 不应因“AI 建议与用户相关”而在甲的首页泄露 |
| 甲修改共同小宇宙故事 | 展示变更、确认后更新，乙看到的共享版本应一致 |
| 甲要求删除自己的私密记忆 | 后端删除/禁用对应未来检索，不继续在群聊调用该信息 |
