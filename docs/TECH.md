# 技术方向｜以低成本 AI 调度为中心

更新：2026-11-16。**技术原则是 AI 驱动整个情侣生态；小宇宙仅是其中一个可以被调用的模块。**

## 现有条件
- 主要开发资源：DSH、Codex；用户预算敏感，不能默认购买昂贵工具或模型。
- 未来考虑 DeepSeek API，但截至目前未接入真实模型；实际模型价格/额度以接入时官方文档为准。
- 无固定前端框架/云厂商/数据库/支付技术选型。

## 推荐概念结构（未实现）
```text
UI：AI 对话/引导 + 动态首页 + 稳定功能入口
                  ↓
意图解释：用户想做什么？属于谁？什么时候？
                  ↓
关系记忆层：个人 / 双方共享 / 单次授权（权限过滤）
                  ↓
AI 功能导演：选择、排序、组合可用模块，生成结构化计划
                  ↓
后端业务校验：权限、预算、动作白名单、必要确认
                  ↓
功能注册表/预制模块
  ├─ 共同计划 / 约会 / 心愿 / 预算
  ├─ 情感沟通 / 关系守护
  ├─ 秘密策划 / 日常灵感
  ├─ 相册回忆 / 故事
  └─ 小宇宙 / 角色 / 场景（独立模块）
                  ↓
用户操作与结果反馈 → 有选择地更新关系记忆
```

### 关键原则
- **模型决定内容与模块选择，前端渲染经过开发的组件**；不让模型任意生成执行脚本。
- 遇到“今晚吃什么”应直接编排餐食/计划模块，不必先在宇宙里创造餐厅。
- UI 动态变化应以有限、清楚、可解释的卡片/模板为起点，支持用户手动切换。
- “实时决策”是交互时依据最新上下文重新计算，不自动等于后台长期运行昂贵 Agent。
- 为四类 AI 能力复用一个模型入口是可行的验证方案，**不必四个独立模型**。

## 建议的结构化意图（示意，未定 schema）
```json
{
  "intent": "plan_date",
  "recommended_modules": ["date_planner", "wishlist", "shared_schedule"],
  "reason": "用户希望周末一起出行",
  "requires_confirmation": true
}
```
具体模块标识和数据结构会在实现时确定。模型输出必须校验，不能据此直接扣费、发送消息或读取无授权隐私。

## 成本控制
1. MVP 前期可用本地规则模拟调度，不消耗 API 费用；这只验证交互形态，不能证明模型智能。
2. 真接入时使用服务端保管 API Key，限额、速率限制、缓存、上下文精简与错误回退。
3. 高频固定功能尽量不调用模型；需要“理解与编排”时才用模型。
4. 需要小宇宙等视觉功能时，可先用预制美术资产/2.5D 场景与参数驱动的表现方式；不让这项功能决定全产品开发成本。
5. 用户记忆采用“允许保存什么、谁能读取、何时忘记”的权限与纠错机制。
6. 日历、消费、分享等有副作用操作，必须由用户明确确认。

## 已有 V0.1（历史局部原型）
- `prototype/v0.1/index.html` 为纯 HTML/CSS/JS 的本地演示。
- 关键词匹配主题星球、回忆/心愿、模板故事、卡片排序，本地 `localStorage`。
- **没有** DeepSeek 接口、用户数据同步、模块调度服务、可控关系记忆、完整四种 AI 能力。
- 可以复用其 UI 或交互零件，但不可再把“主题星球主页”当唯一产品架构。
