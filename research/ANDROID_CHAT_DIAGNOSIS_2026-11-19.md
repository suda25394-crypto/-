# 双生宇宙 Android 0.4.1+5 聊天诊断

2026-11-19 · 发布原件、Android 模拟器、两个合成账号、零次正式模型调用

## 修复决策

**等待最久的是冷启动进群。** 已有登录态、40 条群消息，强停到最新一条出现在 Android 界面的三次结果为 **5.17、6.02、6.49 秒**。复测时，首次健康检查在启动后 3.14–3.66 秒才到达本机服务。当前试用包是 Flutter Debug。真机 Profile 对照应作为冷启动和帧耗时的验收基线，目前的数据不足以把这几秒归因于网络或某个组件。[发布记录](https://github.com/suda25394-crypto/-/releases/tag/android-white-purple-v0.4.1-test.5) · [Flutter 性能测量口径](https://docs.flutter.dev/perf/ui-performance)

**第一刀改 `CloudSession.refresh()` 的通知条件。** 群聊静置时每 4 秒重读整份状态，内容相同也会重建根页面、三个隐藏页和可见区附近的 12 个气泡。只在临时源码中跳过相同状态的广播，三轮每轮跟踪到的 build 从 **19 次降到 0 次**；收到新消息、出现断连、恢复连接时仍各广播一次。每轮仍有 1 个 GET。对方收得慢需要单独解决消息到达通知。

| 优先级 | 建议落点 | 验证方法 |
|---|---|---|
| 1　去掉无变化刷新 | 在 `cloud_session.dart:204` 比较数据和连接状态，仅在变化时通知。把 409 后的重复刷新合一。合并进行中的读取时，若旧 GET 早于写入，保留一次写后的补读。账号、配对或路由模式变化仍由根部处理。[同步](../apps/android/lib/src/services/cloud_session.dart#L204) · [根部订阅](../apps/android/lib/src/client.dart#L76) | 让同一快照返回 3 次，根、隐藏页和气泡的额外 build 都应为 0。注入一条新消息、断连、恢复、切换账号，仍应各自正确更新。409 只对账一次，旧响应不能盖过新写入。 |
| 2　让发送立即可见，保住阅读位置 | 点击时以现有 `request_id` 插入本地待发送气泡；服务回传该编号与权威消息 ID 的映射以便合并。自己发送时回到最新消息；读旧记录遇到对方发言时，以消息 ID 和屏内偏移保住阅读位置。[发送](../apps/android/lib/src/ui/cloud_chat.dart#L103) · [列表](../apps/android/lib/src/ui/cloud_chat.dart#L472) · [服务回执](../services/couple/api.py#L319) | 悬停 POST 以及写后的 GET，自己的待发送气泡均应可见。连续发两条同文、回执晚于轮询、失败重试，数量和状态均需正确。卷到历史中部重跑下文的两步复现。 |
| 3　缩短对方收信等待 | 群消息写入后给有权限的在线会话发变更通知，按会话游标取新消息。连接中断时保留轮询补齐；断线重连按 ID 去重。如果先做第 1 项，接收端仍会等下一个 4 秒周期。[轮询](../apps/android/lib/src/services/cloud_session.dart#L244) · [现有全量接口](../services/couple/api.py#L266) | A、B 两端交错发送，覆盖 4 秒周期内不同相位；分别记 B 的状态到达和 B 的首个气泡帧。比较 P50/P95、空闲请求数，再断线重连核对漏收、重复和私聊隔离。 |

## 测到的等待与掉帧

| 场景 | 中位数（范围） | 终点与样本 |
|---|---:|---|
| 强停后启动，恢复账号进群 | 6.02 s（5.17–6.49） | A 端最新历史消息首次可由 Android 无障碍树读取，3 次，40 条群消息 |
| 群聊调出键盘 | 0.495 s（0.353–0.500） | 触发输入至 Flutter 底部导航因键盘收起；三次均核对 Android 输入法已显示 |
| 群聊切私聊 | 0.227 s（0.220–0.457） | 触发到私聊标题出现在前台语义树，3 次；过场动画可继续 |
| 点普通发送 → 自己的气泡 | 0.413 s（0.348–0.457） | 6 次，在列表底部。只识别显示正文的只读气泡，排除发送中被禁用的输入框，并逐条核实 Android 文本节点 |
| 自己气泡 → B 端收到普通消息 | 1.644 s（0.662–3.692） | 同 6 条；B 端原版 `CloudSession` 收到并解码状态的时刻，第二部手机的屏幕绘制另计 |
| 点发 @DP → 模拟模型开始处理 | 0.180 s（0.175–0.196） | 3 次，终点是模拟提供方进入 `complete`。生产接口为非流式，首 token 时刻未知 |
| 点发 @DP → DP 回复可见 | 1.079 s（1.042–1.142） | 同 3 条，模拟提供方人为等待 650 ms。自己气泡和完整回复在同一轮语义采样出现 |

Flutter VM 的 `Flutter.Frame` 数据来自同一原 APK。两个线程中任一耗时超过 16.67 ms 计为一帧超预算。上翻、下翻各 3 次，共 353 帧，130 帧超预算；UI 耗时 P95 **14.4 ms**，栅格耗时 P95 **31.7 ms**。键盘操作窗口 34 帧中 25 帧超预算，切私聊 50 帧中 26 帧超预算。窗口包含手势、过渡、短暂停留及可能碰上的轮询。滚动时的栅格耗时说明仅压缩 Dart 重建次数还需要实机复测。模拟器软件渲染和 Debug 检查都会影响绝对值，无法据此给发布模式定帧率。

## 已复现的界面问题

1. **发成功，仍看不到自己的消息。** 在群内连续向旧记录方向翻两次，发普通消息。通过测试服务确认写入，输入框清空，窗口中仍是旧消息，手动回到底部才出现刚发的气泡。原 APK 复现，另用 120 条消息的 widget 用例复验，发送前后滚动偏移都为 1,620 dp。[输入框与焦点](../apps/android/lib/src/ui/cloud_chat.dart#L132) · [反向消息列表](../apps/android/lib/src/ui/cloud_chat.dart#L472)
2. **停读旧消息时文字跳位。** 在 120 条的 widget 用例中，将第 96 条置于屏内，保持手指不动，让伴侣新增一条。该条中心从 428 dp 移到 349 dp，上移 79 dp，列表偏移仍为 1,560 dp。当前反向列表按最新下标重新定位条目，缺少稳定的阅读锚点。这两项是本次独立发现，用户原先遇到的 bug 仍待识别。[取行逻辑](../apps/android/lib/src/ui/cloud_chat.dart#L497)

旧群消息另有**明确的产品范围**。用 R2 生产上游适配器和遵守分页的模拟 WebUI，A 连发 51 条顶层消息，B 连读三次，各次只见 2–51。项目约定为最近 50 条主消息及各线程最近 50 条回复，完整历史留在 WebUI。Android 没有向前翻页的请求，这解释了为什么早期消息在 App 内到不了；本实验没有发现服务端记录被删除。[上游约定](../services/couple/UPSTREAM.md#L26) · [适配器](../services/couple/upstream.py#L299)

**实际运行。** 同一台 ChatLab 模拟器成功安装并启动 Twoo。单次冷启动的 Android Activity `TotalTime` 为 1,899 ms，进入隐私同意页。点《隐私政策》可打开说明；关闭后点“不同意”，应用退出。此页无访客聊天入口；结合 #25302/25303 的匿名登录路由，推测正常进入聊天需要有效会话。手头没有 Twoo 测试账号，因此聊天操作和相同消息量的横向速度比较留空。该 1,899 ms 的终点也不同于自家测试的进群可读。

**适合 Flutter 借鉴的三处**是用 ID 合并待发送气泡、在线收变更通知并以游标补缺、切回会话时先展示按账号隔离的内存数据。前两项分别解决本方回显与对端等轮询。第三项配合历史分段加载才能兼顾切页和深翻；内存缓存只覆盖同一进程。我们已有 `ListView.builder` 与按账号和会话区分的 `PageStorageKey`，本次数据支持继续用 Flutter。
